# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
./gradlew build           # compile and check
./gradlew deploy          # deploy to roboRIO (robot must be reachable)
./gradlew simulateJava    # run desktop simulation (opens GUI + DriverStation)
./gradlew replayWatch     # replay a .wpilog log file against current code
./gradlew test            # run JUnit 5 tests
```

There is no linter configured. The project targets Java 17.

## Architecture

This is a WPILib 2026.2.1 command-based robot project for FRC Team 1405. Key libraries: CTRE Phoenix 6 (motors + swerve), PathPlanner, PhotonVision, AdvantageKit.

### Subsystem IO pattern

Every hardware subsystem follows the AdvantageKit IO layer pattern:

- `FooIO.java` — interface + inner `@AutoLog`-annotated `FooIOInputs` class. All hardware reads go into `inputs`; all hardware writes go through interface methods.
- `FooIOTalonFX.java` — real-hardware implementation (TalonFX motors).
- `FooIOSim.java` — simulation implementation (physics model, no hardware).
- `Foo.java` — subsystem that holds `FooIO io` and `FooIOInputsAutoLogged inputs`, calls `io.updateInputs(inputs)` then `Logger.processInputs(...)` each periodic cycle, and exposes `Command`-returning factory methods.

`RobotContainer` instantiates each subsystem by selecting real vs. sim IO at startup: `RobotBase.isReal() ? new FooIOTalonFX() : new FooIOSim()`.

### Logging (AdvantageKit)

`Robot` extends `LoggedRobot`. All logging is set up in `Robot()` before any other initialization. On the real robot, logs write to `/home/lvuser/logs/` (both AdvantageKit `.wpilog` and CTRE Hoot `.hoot` format). In simulation, if a `.wpilog` replay file is found it runs deterministic replay; otherwise it publishes to NT.

To log a field: add `@AutoLogOutput(key = "Subsystem/FieldName")` to any instance field in a `SubsystemBase` subclass (generated by the `akit-autolog` annotation processor at build time). For one-off values: `Logger.recordOutput("Key", value)`.

**Critical replay boundary:** In `Vision.periodic()`, `Logger.processInputs()` must be called before any filter logic. This is what makes vision filter tuning replayable — changing a threshold and running `simulateJava` against a real match log will show the new behavior without re-running on the robot.

### Vision

`Vision.java` drives all AprilTag-based pose estimation. Flow each loop:
1. Each `VisionIO` calls `updateInputs()` to populate raw pose estimates (pre-filter, stored in `VisionIOInputs`).
2. `Logger.processInputs()` records the raw inputs — replay boundary.
3. Filter pipeline runs: boundary rejection → velocity jump rejection → trust scalar computation (area, pixel offset, aspect ratio, velocity weights).
4. Accepted samples are queued in `samples`; `RobotContainer.correctOdometry()` drains them and calls `drivetrain.addVisionMeasurement()` with computed XY and theta stddevs.

Camera configs (names, transforms, intrinsics) live in `VisionConstants.CONFIGS`. Two cameras: `"Left"` and `"Right"`.

### Feature switches

`constants/FeatureSwitches.java` contains `public static final boolean` flags. All vision improvement candidates (P1/P2/P3) are switches that default to `false` (2026 behavior baseline), allowing scientific A/B comparison against real match logs. See `docs/vision-testing-protocol.md` for the measurement methodology.

### Swerve drivetrain

`CommandSwerveDrivetrain` extends the CTRE-generated `TunerSwerveDrivetrain`. Swerve constants (PID gains, module geometry, CAN IDs) are in `generated/TunerConstants.java` — this file is normally regenerated by CTRE Tuner X, not hand-edited. The `TunerConstants_OldRobot.java` file is preserved for reference.

### Key files

| File | Purpose |
|------|---------|
| `Constants.java` | CAN IDs, PID gains, shooter speeds, robot physical properties |
| `constants/FeatureSwitches.java` | Boolean flags for all conditional behaviors |
| `constants/FieldConstants.java` | Field geometry, scoring positions |
| `lib/LerpTable.java` | Piecewise linear interpolation — used throughout vision filtering and drive scaling |
| `lib/AllianceSymmetry.java` | Flips coordinates for red alliance |
| `lib/Tracer.java` | Lightweight periodic trace timer (wraps AKit Logger) |
| `generated/TunerConstants.java` | Auto-generated swerve config — regenerate with Tuner X for 2027 |

### Coprocessor

`coprocessor/orangepi-nt-publisher.py` runs on the Orange Pi alongside PhotonVision, publishing CPU/RAM/disk/temp to NT4 under `/OrangePi/`. Managed as a systemd service (`orangepi-nt-publisher.service`).

### Tools

`tools/vision-analyzer/analyze.py` — zero-dependency Python script that parses `.wpilog` files and generates an interactive HTML dashboard (Plotly.js). Run against logs from `/home/lvuser/logs/` on the roboRIO to visualize vision acceptance/rejection, pose estimates, and correction magnitudes.
